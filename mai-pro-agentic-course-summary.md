### 1. What’s Cool About Agents

This slide compares **Basic LLM**, **RAG** and **Agent** architectures.

* **Basic LLM**: a simple chain where a prompt goes into an LLM and an answer comes out. There is no memory or external context.
* **RAG**: adds a retrieval step—documents are encoded into embeddings, stored in a vector database, and relevant context is fetched and appended to the prompt before passing it to the LLM. This grounds answers in external knowledge.
* **Agent**: expands on RAG by adding **memory**, **reasoning** and **tools**. A prompt enters the LLM; the agent reasons about the task, consults or updates persistent memory, calls external tools (APIs, search, etc.) as needed, and then produces an answer and possibly takes an **action**.

### 2. Agent Architecture

This slide breaks an autonomous agent into four fundamental components and explains how they interact in a continuous loop.

* **Profile**: defines the agent’s personality, demographics and goals. Profiles can be handcrafted, LLM-generated or learned from data.
* **Memory**: provides continuity. It ranges from short-term (current conversation) to long-term stores and reflective synthesis of experiences.
* **Planning**: the reasoning engine that decomposes tasks, evaluates approaches and adapts based on feedback. Variants include single‑path (chain-of-thought), multi‑path (tree of thoughts) and planning with feedback.
* **Action**: executes plans via tools (APIs, code execution, web browsing), environment manipulation (file systems, databases) or communication channels.
  The slide emphasises that these components operate in a **continuous loop**—profile shapes behaviour, memory gives context, planning decides what to do, and action executes, with outcomes feeding back into memory.  A table compares how frameworks implement these components: LangChain uses system prompts, conversation memory and an AgentExecutor; AutoGen has agent configs and GroupChat; CrewAI uses role/backstory, crew memory and task delegation; the Claude SDK includes an agentic loop and tool use.

### 3. Agent Capabilities Spectrum

An interactive slider shows eight dimensions separating a simple chatbot from a full agent:

1. **Goal Complexity:** from low-level requests to high-level, open-ended goals.
2. **Execution Pattern:** one-shot responses vs iterative loops.
3. **Task Planning:** none vs task decomposition.
4. **Tool Use:** text-only vs multi-tool integration.
5. **Feedback Loops:** no feedback vs continuous feedback.
6. **Memory:** stateless vs persistent memory.
7. **Data Access:** training data only vs real-time data (APIs, RAG).
8. **Interaction Model:** synchronous chat vs asynchronous workers embedded in other tools.
   The slide traces the evolution from a simple chatbot (Q&A only) → assistant (adds instructions) → RAG (adds knowledge retrieval) → agent (adds tools and loop) → multi-agent (adds coordination). A key insight: choose the simplest model that fits the task—chatbots for straightforward Q&A, RAG for knowledge lookup, agents for multi-step tasks and multi-agent systems for complex workflows.

### 4. Agentic Patterns

This suite of mini‑slides explains common reasoning/acting patterns used by agents:

* **ReAct:** interleaves reasoning and actions; the agent thinks, acts via a tool, observes results and repeats.
* **Chain‑of‑Thought:** the model shows its step-by-step reasoning before giving an answer.
* **Reflexion:** a self‑reflection loop where the agent produces an output, evaluates it, and refines based on evaluation.
* **Plan‑and‑Execute:** the agent first creates a complete plan, then executes each step; useful for complex multi-step tasks.
* **Tree of Thoughts:** explores multiple reasoning branches like a search tree, backtracking when necessary; good for problems with many possible approaches.
* **LATS (Language Agent Tree Search):** combines Monte Carlo tree search with ReAct; the agent tries different action paths, evaluates outcomes and backpropagates success scores.
* **Self‑Discover:** the agent discovers which reasoning modules are relevant for the task, composes them and executes; adapts its reasoning strategy per task.
* **Orchestrator‑Workers:** a lead agent decomposes tasks and delegates subtasks to specialised worker agents that run in parallel and report back.

### 5. Multi‑Agent Coordination

This slide explores patterns for coordinating multiple agents:

* **Blackboard:** agents share a central workspace; each agent monitors the board and contributes when they can. Decentralised decision‑making around a central knowledge store.
* **Supervisor (Hierarchical):** a central orchestrator assigns work to specialised workers and synthesises results. Clear chain of command, appropriate when tasks need management.
* **Swarm (Decentralised):** peer agents communicate locally with no central control; inspired by ant colonies and bees, yielding emergent global behaviour.
* **Debate / Discussion:** agents with different viewpoints argue and critique; a judge or consensus mechanism selects the best solution.
* **Pipeline (Sequential):** agents are arranged in a chain, each processing the output of the previous one like an assembly line.
* **Hybrid (Adaptive):** combines multiple patterns dynamically—e.g., a supervisor for high-level planning, swarm for exploration and debate for quality—sometimes referred to as the “Arbiter” pattern.

### 6. Agentic RAG

An illustrated flow compares **Traditional RAG** and **Agentic RAG**. In traditional RAG, documents are embedded and indexed in a vector database; a query is embedded, a search retrieves context, and the LLM uses this context to generate a final answer. In **Agentic RAG**, the LLM agent plays a larger role: it rewrites the query, determines whether more detail is needed, chooses which source (vector DB, APIs, web) to query, retrieves information, prompts the LLM, evaluates whether the answer is sufficient and iterates if necessary. The key insight: the agent decides **when** and **where** to retrieve information, validating the answer at each step.

### 7. Human‑in‑the‑Loop Patterns

This slide categorises six ways humans interact with agents along an **automation spectrum**:

1. **Fully Autonomous:** agent handles low‑risk, high‑volume tasks without human involvement (e.g., email sorting, log analysis).
2. **Human Oversight:** agent acts autonomously but a human monitors and can intervene (content moderation, code generation).
3. **Human Approval:** the agent proposes an action, but a human must approve before execution (financial transactions, legal documents).
4. **Collaborative:** human and agent iterate together on creative or strategic tasks.
5. **Escalation Pattern:** agent handles routine cases and escalates edge cases to a human reviewer (support tickets, fraud detection).
6. **Guardrails Pattern:** pre‑ and post‑checks ensure safety; automated checks can block unsafe agent actions.
   The slide offers examples of when to use each pattern.

### 8. Gen AI Impact Framework

This framework illustrates the AI value chain from a **power concentration** perspective. Levels include:

* **Innovators:** a small group of companies developing foundational models (e.g., OpenAI, Anthropic, Google DeepMind).
* **Builders:** companies building products and applications on top of LLMs (e.g., Microsoft Copilot, Cursor, Perplexity).
* **Enablers:** infrastructure providers offering cloud services, orchestration tools and vector databases (e.g., AWS Bedrock, Azure AI, Google Vertex AI).
* **Customizers:** consultants and firms delivering tailored AI solutions and enterprise integrations (e.g., Accenture, Deloitte, McKinsey QuantumBlack).
* **Utilizers:** enterprises deploying AI internally to improve efficiency (e.g., JP Morgan Chase, Goldman Sachs).
* **Guardians:** organisations focused on AI safety, ethics and compliance (e.g., Anthropic’s safety team, Arthur AI, Fiddler AI).
  Power is concentrated at the top and distributed at the bottom. The key message for business leaders: most companies are **Utilizers**—they don’t need to build models, just leverage them effectively. They should partner with **Customizers** for implementation, use **Enablers** for infrastructure, and engage **Guardians** for compliance.

In multi‑agent systems, routing and branching underpin techniques like pipelines (sequential processing) or hub‑and‑spoke architectures.                                                                                                                                              |

Workers can run in parallel but follow the supervisor’s plan.                                                                                                                                                                                          |

Many simple agents operate with local rules and communicate peer‑to‑peer; complex behaviour emerges from their interactions. These summaries should give you a comprehensive reference for concepts related to large language models (LLMs), covering model types, training techniques, prompting, inference and retrieval‑augmented generation (RAG).

| Term                                     | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Foundation Model**                     | A foundation model is a large neural network trained on diverse, general‑purpose data (text, code and sometimes images or audio) to learn broad representations of language and knowledge. This pretraining provides the model with versatile capabilities (e.g., translation, summarization, reasoning) that can be adapted to many downstream tasks. Foundation models power most modern LLMs and form the base upon which fine‑tuning or prompting builds task‑specific performance.                                                                      |
| **Multi‑Modal Models**                   | Multi‑modal models are machine‑learning systems that can process and generate multiple data types—such as text, images, audio or video—in a unified architecture. They are trained on datasets that align different modalities (e.g., image–caption pairs) so they can understand and reason across modalities. Examples include OpenAI’s GPT‑4 with vision and Google’s Gemini, which enable tasks like describing images, answering questions about charts and generating captions.                                                                        |
| **Reasoning Models**                     | Reasoning models are LLM variants optimized for logical problem solving and stepwise thinking. They often incorporate techniques like chain‑of‑thought prompting, self‑reflection or tree‑of‑thoughts to break complex problems into subtasks. Recent research (e.g., Anthropic’s Claude 2 and OpenAI’s o‑series models) explores training methods that encourage longer internal thought processes, improving performance on reasoning‑intensive tasks such as math proofs, coding and strategic planning.                                                  |
| **Instruction‑Tuned Models**             | Instruction‑tuned models are LLMs fine‑tuned on curated datasets of task instructions and desired outputs. The goal is to align the model’s behavior with human intent: when given a clear instruction (“summarize this article”, “translate to French”), the model follows it faithfully. This tuning improves the model’s helpfulness and reduces unsafe or irrelevant responses compared with raw foundation models.                                                                                                                                      |
| **LLM vs SLM**                           | “LLM” stands for Large Language Model, typically referring to models with billions of parameters trained on broad corpora. “SLM” means Small Language Model; it has far fewer parameters (millions rather than billions) and can run efficiently on edge devices or local servers. SLMs trade accuracy and breadth of knowledge for speed, privacy and lower hardware requirements, making them suitable for on‑device applications or low‑latency tasks.                                                                                                    |
| **Model Size (7B, 70B, 40B)**            | Model size denotes the number of trainable parameters in an LLM. Sizes like 7 billion, 40 billion or 70 billion parameters convey the model’s capacity: larger models generally achieve better performance and reasoning abilities because they can learn more complex patterns. However, bigger models require more computation, memory and power, so deployment involves balancing performance, cost and latency.                                                                                                                                          |
| **Pre‑Training**                         | Pre‑training is the initial phase where a model learns general language patterns by predicting masked tokens or the next word across massive text corpora. This unsupervised learning stage imbues the model with world knowledge, grammar and basic reasoning skills. Pre‑trained models can then be adapted to specific tasks through fine‑tuning or prompting.                                                                                                                                                                                            |
| **Fine‑Tuning (LoRA, QLoRA)**            | Fine‑tuning adapts a pre‑trained model to a narrower task or domain using additional labeled data. Techniques like LoRA (Low‑Rank Adaptation) and QLoRA (Quantized LoRA) insert small trainable layers into the network or quantize weights to reduce computational cost while retaining performance. These approaches make it feasible to customize large models on modest hardware without retraining all parameters.                                                                                                                                      |
| **RLHF / DPO**                           | Reinforcement Learning from Human Feedback (RLHF) is a training method where human evaluators rank model outputs, and these preferences guide a reinforcement‑learning algorithm to adjust the model to align with human values (as used in ChatGPT). Direct Preference Optimization (DPO) is a more recent technique that directly optimizes the model’s parameters to satisfy preference comparisons without an explicit reward model. Both aim to produce models that are safer, more helpful and less likely to generate harmful or nonsensical content. |
| **Benchmark & Evaluation**               | Benchmarking involves testing LLMs on standardized datasets and tasks to measure performance, such as MMLU for knowledge, GSM8K for math and HellaSwag for commonsense reasoning. Evaluation metrics may be accuracy, F1 score, BLEU or more specialized measures (e.g., pass@k for code). Consistent benchmarking helps researchers compare models, track progress and identify strengths and weaknesses.                                                                                                                                                   |
| **Guardrails**                           | Guardrails are policies and technical measures that constrain an LLM’s outputs to prevent harmful, unethical or unwanted responses. They include content filters, prompt injection defences, safety classifiers, rate limits and domain‑specific restrictions (e.g., disallowing medical advice or personal data leakage). Implementing guardrails is essential for deploying LLMs in enterprise and consumer applications safely.                                                                                                                           |
| **System Prompt**                        | A system prompt is a hidden instruction given to an LLM that sets its overall behavior and persona before the conversation begins. It defines boundaries, style and tone—such as “You are a helpful assistant that answers concisely and politely.” System prompts establish context and ensure consistent responses across sessions, especially in agentic systems with multiple tools.                                                                                                                                                                     |
| **User Prompt**                          | The user prompt is the input text provided by the user or calling application at inference time. It expresses the task or question the model should address. The model combines the system prompt (if any) with the user prompt to generate a response; good prompt design is crucial for obtaining accurate, relevant outputs.                                                                                                                                                                                                                              |
| **Few‑Shot / Zero‑Shot**                 | Zero‑shot prompting asks the model to perform a task without providing examples (“Translate this to Spanish”), relying on its pretrained capabilities. Few‑shot prompting gives the model a handful of input–output examples within the prompt to illustrate the desired behavior, improving accuracy when the model hasn’t been explicitly trained on that task. Both methods leverage the model’s generalization abilities and reduce the need for fine‑tuning.                                                                                            |
| **Chain of Thought**                     | Chain‑of‑thought (CoT) prompting encourages the model to articulate its reasoning steps explicitly before delivering a final answer. By decomposing problems into intermediate steps, models often achieve better accuracy and reduce hallucinations on tasks like math, logic and question answering. However, CoT outputs can be verbose and may reveal sensitive intermediate reasoning if not handled carefully.                                                                                                                                         |
| **Token (Input/Output)**                 | Tokens are the atomic units of text that an LLM processes—often sub‑word chunks rather than whole words. During inference, input tokens are fed to the model, and it predicts a distribution over the next possible output token. The number of input tokens affects cost and latency; the model’s maximum output tokens limit response length.                                                                                                                                                                                                              |
| **Top‑k / Top‑p Sampling**               | Top‑k sampling restricts the model to choose from the k most probable next tokens, while top‑p (nucleus) sampling selects from the smallest set of tokens whose cumulative probability exceeds p (e.g., 0.9). These methods inject randomness into generation by preventing the model from always picking the single highest‑probability token, yielding more diverse and natural responses. They also control the trade‑off between creativity and coherence.                                                                                               |
| **Temperature**                          | Temperature is a hyperparameter that scales the logits (pre‑softmax activations) before sampling. Lower temperatures (e.g., 0.2) make the model more deterministic by sharpening the probability distribution around the highest‑probability tokens, whereas higher temperatures (e.g., 1.0 or 1.5) flatten the distribution and increase randomness. Adjusting temperature allows users to tune generation style from conservative to creative.                                                                                                             |
| **Max Tokens**                           | Max tokens specifies the maximum number of tokens the model will generate in response to a prompt. It acts as a hard cap to prevent overly long outputs and control computational cost. Selecting an appropriate value depends on the task: short for concise answers, longer for detailed essays or code.                                                                                                                                                                                                                                                   |
| **Context Window**                       | The context window defines the total number of tokens (input plus generated output) the model can consider at once. Larger context windows allow the model to remember longer conversations or documents but increase memory usage and inference time. Models like GPT‑4 and Claude 3 offer context windows ranging from thousands to hundreds of thousands of tokens.                                                                                                                                                                                       |
| **Latency**                              | Latency measures the time it takes for an LLM to produce a response after receiving a prompt. Factors affecting latency include model size, compute hardware, network overhead, prompt length and sampling parameters. Low‑latency responses are critical for real‑time applications, while research tasks can tolerate longer processing times.                                                                                                                                                                                                             |
| **Hallucination**                        | Hallucination occurs when an LLM confidently generates information that is false, unsupported or nonsensical. It stems from the model’s reliance on statistical patterns rather than factual grounding. Mitigation strategies include retrieval‑augmented generation, fact‑checking, calibrated prompting and post‑processing verification.                                                                                                                                                                                                                  |
| **RAG (Retrieval‑Augmented Generation)** | RAG is an architecture that combines an LLM with a retrieval system to ground outputs in external knowledge. At inference time, the model queries a vector database or search engine, retrieves relevant documents and feeds them alongside the prompt. By incorporating real data, RAG reduces hallucinations and extends the model’s knowledge beyond its training cut‑off.                                                                                                                                                                                |
| **Chunking**                             | In RAG systems, documents are split into smaller “chunks” (e.g., paragraphs or sentences) before being embedded into vector space. Chunking improves retrieval granularity and reduces irrelevant context in the prompt. The chunk size is a trade‑off: too small and you lose context; too large and you risk bringing in extraneous information.                                                                                                                                                                                                           |
| **Re‑Ranking**                           | Re‑ranking is the process of ordering retrieved documents or chunks based on relevance before feeding them to the LLM. After an initial search retrieves candidate passages, a secondary model or heuristic scores them to select the most pertinent information. Re‑ranking improves answer quality by prioritizing the best evidence and discarding irrelevant results.                                                                                                                                                                                    |
| **Vector DB**                            | A vector database stores high‑dimensional embeddings of text (or other data) and supports efficient similarity search. It allows rapid retrieval of documents whose embeddings are close to a query embedding, which is critical for RAG systems. Popular vector DBs include Pinecone, Milvus, FAISS and Chroma; they handle indexing, storage, filtering and scaling for millions or billions of vectors.                                                                                                                                                   |
| **Retrieval**                            | Retrieval refers to the process of fetching relevant information from a data store (vector DB, search engine, knowledge base) to augment a language model’s response. It usually involves embedding the query, performing similarity search, filtering by metadata and preparing the retrieved text for the prompt. Good retrieval is essential for RAG systems to ground responses in factual sources.                                                                                                                                                      |
